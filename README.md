# 屋内ドローン フライトシミュレータ

**フォトリアルな画像からの自己位置推定 (visual localization / VIO / SLAM) 研究のための、屋内マルチコプタ用シミュレータ。**

ブラウザだけで動きます。ビルド不要・追加インストール不要・オフラインで動作します。

- 機体の**見た目とパラメータをその場で変更**できます (プリセット 9 種、パーツごとに形状・寸法・色・質量を編集)
- パーツを変えると**慣性テンソルや推力重量比も自動で再計算**され、飛び方が変わります
- 環境は**単室 7 種**と、階段室・吹抜で上下階を行き来できる**複数階の建物 4 種**
- 搭載カメラは**レンズ歪み・周辺減光・センサノイズ・モーションブラー**まで再現します
- 飛行データを **TUM / EuRoC / COLMAP / NeRF 形式**のデータセットとして書き出せます

---

## クイックスタート

Node.js 18 以降が必要です。**外部パッケージのインストールは不要**です
(three.js と lil-gui は `vendor/` に同梱済み)。

```bash
git clone <このリポジトリ>
cd realmultucoptersimulator
npm start           # → http://127.0.0.1:8080/ をブラウザで開く
```

これだけで飛ばせます。まずは次の 3 つを試してください。

### 1. 飛ばしてみる (1 分)

1. ブラウザで開く → 右パネル「機体 → プリセット」で機体を選ぶ
2. **Space** で離陸 (既定は位置保持モードなので、放っておいてもホバリングします)
3. **↑↓←→** で移動、**W/S** で昇降、**A/D** で旋回
4. **V** で視点切替 — 「機体カメラ」にすると、そのままデータセットになる映像が見えます

### 2. データセットを 1 本作る (3 分)

1. 右パネル「飛行 → モード」を **自動飛行 (auto)** にする
2. 「飛行 → 自動飛行の軌道 → パターン」で **往復スキャン** を選ぶ
3. 「データセット記録」で fps と枚数を決めて **記録 開始** (または **G** キー)
4. 貯まったら **ZIP で書き出し**

ZIP には画像・真値軌跡・IMU・カメラ内部パラメータ・COLMAP / NeRF 形式のポーズが
すべて入っています → [データセットを作る](#データセットを作る)

### 3. 複数階の建物を点検飛行する (2 分)

1. 「環境 → 環境の種類」を **建物 (複数階)** にする
2. 「環境 → 建物」で **工場** を選ぶ
3. 「飛行 → モード」を **自動飛行**、「パターン」を **建物ルート**、「ルート」を **設備点検**

生産エリアを低空で見て回ってから、高さ 4.5 m のキャットウォークまで上がって
配管を点検する経路を飛びます → [建物を作る・再現する](#建物を作る再現する)

## 画面の見方

画面は 3 つの領域に分かれています。

**画面上部のボタン** — 視点 / 一時停止 / リセット / 記録 / 書き出し / 操作方法 / 設定

**画面左の計器表示 (HUD)** — 3 段組みです。

| 段 | 内容 |
|---|---|
| 飛行状態 | 時刻・モード・位置・対地高度・速度・姿勢・角速度・風速・接触・描画 fps |
| ロータ出力 | 各ロータの出力バー・電圧・電流・バッテリー残量・消費電力・回転数 |
| 機体諸元 | 質量・ロータ数・最大推力・推力重量比・ホバリング出力・ホバリング時間・ディスク荷重・慣性・カメラ |

機体を編集すると諸元が即座に更新されるので、設計の妥当性をここで確認できます。

- **推力重量比** — 2.0 以上が扱いやすい目安 (1.5 未満は赤字で警告)
- **ホバリング出力** — 40〜60% が健全
- **ホバリング時間** — バッテリー容量と消費電力からの推定

**画面右下の小窓 (PiP)** — 機体カメラの映像です。
**これがそのままデータセットの画像になります** (歪み・ノイズ・ブラー込み)。
「表示 → カメラ映像を重ねる」で消せます。

**画面右のパネル (設定 GUI)** — 8 つの folder に分かれています。

| folder | 中身 |
|---|---|
| **機体** | プリセット / フレーム (配置・アーム長・慣性) / パーツ (形状・色・質量) / 動力系 / 空力 / 制御 |
| **環境** | 環境の種類 (単室 ⇄ 建物) / 部屋・建物 / 寸法 / 模様の多さ / 家具の量 / マーカー / 照明 |
| **搭載カメラ (画像生成)** | プリセット / 解像度・画角 / レンズ歪み / センサ特性 / モーションブラー / 深度 |
| **飛行** | フライトモード / 自動飛行の軌道 (パターン・ルート・速度・高度・ヨー) |
| **シミュレーション** | 時間倍率 / 物理レート / 室内気流 / 故障注入 / 推定値で制御 |
| **データセット記録** | fps / 枚数 / 画像形式 / 深度保存 / 記録開始・ZIP 書き出し |
| **表示** | 視点 / PiP / カメラ更新レート / 軌道・履歴・当たり判定の表示 |
| **設定の保存 / 読み込み** | 全設定を JSON で保存・復元 |

各 folder はタイトルをクリックで折りたためます。
画面上部の「設定」ボタンでパネル全体を隠せます (データセットの見た目を確認したいとき)。

## 操作方法

| キー | 動作 |
|---|---|
| W / S | 上昇 / 下降 |
| A / D | 左旋回 / 右旋回 |
| ↑ / ↓ | 前進 / 後退 |
| ← / → | 左移動 / 右移動 |
| Shift | 微速モード |
| Space | 離陸 / 着陸 |
| M | フライトモード切替 |
| V | 視点切替 (自由 / 追従 / 機体カメラ / 俯瞰 / コックピット) |
| P | 一時停止 |
| R | リセット |
| G | データ記録の開始 / 停止 |
| H | ヘルプ |

ゲームパッドを接続すると自動で認識します (Mode 2 配置)。

**フライトモード**

| モード | 挙動 | 向いている用途 |
|---|---|---|
| `position` 位置保持 | スティックを離すとその場に留まる | 屋内での撮影・手動操作 |
| `auto` 自動飛行 | 軌道パターンを自動追従 | **データセット収集** |
| `altitude` 高度保持 | 高さだけ自動、水平は手動 | 手動でスキャンしたいとき |
| `angle` 姿勢制御 | スティック = 傾き | 一般的な FPV 操作 |
| `rate` アクロ | スティック = 角速度 | 制御の限界を見たいとき |

**Space (離陸 / 着陸)** は建物モードでは**今いる階の床**を基準にします。
3 階にいるときは 3 階の床から 1.2 m 上がります。

## 機体を作る

右パネルの「機体」から編集します。値を変えると
**メッシュ・質量・重心・慣性テンソル・ミキサ・制御ゲインがすべて再計算**されます。

たとえばアーム長を 2 倍にすると慣性モーメントが約 4 倍になり、
姿勢の応答が目に見えて鈍くなります。

### プリセット

| プリセット | 質量 | 特徴 |
|---|---|---|
| **StampFly (M5Stack)** | 35 g | 公式 StampFly Ecosystem の実測パラメータをそのまま使用 |
| トイドローン 90mm | 101 g | Tello クラス。プロペラガード付き、前方カメラ |
| ナノ機 65mm | 37 g | Crazyflie クラス。狭所・群制御向け |
| シネフープ 3インチ | 421 g | 全周ダクト。屋内で安全、映像取得向け |
| フリースタイル 5インチ | 628 g | 一般的な FPV 機。推力重量比が高い |
| 研究用 250mm | 774 g | 下向きステレオカメラ + ガード。自己位置推定の実験機 |
| ヘキサコプター | 2.11 kg | 6 発。1 基停止時の挙動も再現できる |
| X8 同軸反転 | 3.62 kg | 8 発コアキシャル |
| トライコプター | 539 g | 3 発 + テールサーボ。非対称機体 |

### パーツを変える

パーツは**形状・寸法・色・材質・質量**を個別に変更できます。

| パーツ | 選べる形状 |
|---|---|
| ボディ | 直方体 / 角丸 / 円柱 / 球 / 板 / くさび / ドーム |
| アーム | パイプ / 角材 / テーパー / 平板 / トラス |
| モータ | ベル / 円柱 / 箱 / コアレス |
| プロペラ | 2枚 / 3枚 / 4枚 / ディスク / ダクテッド(5枚) |
| プロペラガード | リング / 八角 / ケージ / ダクト / バンパー |
| 脚 | スキッド / 脚 / パイプ / リング / パッド |
| カメラ | 箱 / 円筒 / ドーム / ジンバル / ステレオ |

色は各パーツについて、ベースカラー・金属度・粗さ・クリアコート・発光色・
不透明度を個別に指定できます (例: カーボンのアームに赤いモータベル、
半透明のプロペラ、光る LED)。

ロータ配置はクアッド X / + / H / デッドキャット / トライ / ヘキサ X / + /
オクタ X / X8 同軸反転から選べ、アーム長・ロータ傾斜・配置角も変更できます。
**ミキサ (制御配分) は配置から自動生成される**ので、どの構成でも飛びます。

### 制御ゲインは自動で決まります

機体の慣性モーメントとモータ時定数から角速度ループの交差角周波数を
`ω = 1/(1.5 τ_motor)` に置き、微分ゲインでモータの極を相殺します。
姿勢 → 速度 → 位置と帯域を 2.5 分の 1 ずつ下げてカスケードを組むので、
37 g のナノ機から 3.6 kg の X8 まで同じコードで安定して飛びます。

「機体 → 制御 → 応答の機敏さ」で全体の帯域をまとめて上下できます
(手動で詰めたい場合は「ゲイン自動調整」を切ります)。

作った機体は「設定の保存 / 読み込み」から JSON で保存できます。

### StampFly (M5Stack)

物理パラメータは、公式の
[StampFly Ecosystem](https://github.com/M5Fly-kanazawa/stampfly_ecosystem)
のシミュレータが使っている**実測値をそのまま採用**しています。

| 項目 | 値 | 備考 |
|---|---|---|
| 質量 | 0.035 kg | |
| 慣性テンソル | diag(9.16e-6, 13.3e-6, 20.4e-6) kg·m² | ロール/ピッチ/ヨー |
| ロータ位置 | (±23, ±23, 5) mm | アーム長 32.5 mm |
| 推力係数 | Ct = 6.7e-9 (T = Ct·ω²) | 2026-07-15 ベンチ実測 |
| トルク係数 | Cq = 4.10e-11、κ = 6.12e-3 | ファームのミキサ定数と一致 |
| ロータ慣性 | Jmp = 1.375e-8 kg·m² | |
| モータ | Rm = 0.63 Ω, Ke = 5.5e-4, 716-17600KV | 3.8 V で約 41,600 rpm |
| バッテリー | 1S 300 mAh HV | |

推力重量比 1.49 / ホバリング約 34,200 rpm (出力 82%) と、実測モデルと一致します
(`tests/vehicle.test.js` で数値を固定しています)。ロータの回転方向もファームウェアの
1_FR / 2_RR / 3_RL / 4_FL と揃えてあります。

**見た目は実機の CAD (STL) をそのまま使っています。** 公式ランディングページと同じ
STL パーツ (フレーム / 基板 / M5StampS3 / バッテリー / モータ×4) を `assets/stampfly/`
に同梱し、プロペラだけは STL が平板なので 3 枚羽根 (半径 14.99 mm) を生成しています。
STL の実寸は 81.8 × 31.5 × 81.8 mm で、カタログ値 (82 × 82 × 30 mm) と一致します。
各パーツの色は「機体 → パーツ → 実機3Dモデル」から変更でき、
STL を無効にすればパラメトリックな形状に戻せます。

実機にはカメラが無いため、研究用に小型カメラを載せた構成にしています
(取り付け位置・俯角は GUI から変更できます)。
外周フレームは当たり判定にも反映していて、中心から 41.0 mm — 実機の 81.8 mm 角と一致します。

実機に合わせて調整するときの注意点は
[docs/RESEARCH.md の「StampFly を使う場合」](docs/RESEARCH.md#6-stampfly-を使う場合)
にまとめてあります。

## 環境を作る

環境は **単室** と **建物 (複数階)** の 2 種類から選べます
(「環境 → 環境の種類」で切り替え)。

### 単室

部屋 7 種 (研究室 / 体育館 / 廊下 / 倉庫 / 空室 / リビング / 工場)。
寸法・家具・マーカーを自由に変えられます。

自己位置推定の研究で重要な「見た目の情報量」を独立に変えられます:

| つまみ | 範囲 | 効果 |
|---|---|---|
| 模様の多さ | 0 〜 2 | 0 = のっぺりした壁、2 = 模様の多い床 |
| 家具の量 | 0 〜 3 | 0 = 何もない部屋、3 = 雑然とした倉庫 |
| マーカー枚数 | 0 〜 24 | AprilTag 風のフィデューシャルマーカーを壁と床に配置 |
| ポスター枚数 | 0 〜 20 | 壁の掲示物。特徴点を増やすが、マーカーと違って既知のパターンではない |
| 窓の数 | 0 〜 8 | 外光の入り方が変わる (逆光条件を作れます) |
| 照明 | 7 種 | 蛍光灯 / 暖色 / 高天井灯 / 廊下灯 / 単灯 / 混合光源 / 薄暗い |
| 明るさ倍率 | 0.05 〜 3 | 低照度条件を作る。暗いほどノイズが相対的に大きくなります |

「空室 + 模様 0」にすれば特徴点がほとんど無い条件を、
「倉庫 + 模様 2 + マーカー 12」にすれば特徴点が豊富な条件を作れます。

**乱数シード**を変えると家具とマーカーの配置が変わります
(同じシードなら必ず同じ配置になります)。
「同じ条件・違う配置」のバリエーションはこれで作ります。

床・壁・天井のテクスチャはすべて**その場で生成**しています
(外部画像ファイルはありません)。カラー・法線・粗さの 3 種類のマップを
生成するので、照明に対して自然に反応します。

### 建物 (複数階)

4 種。すべて 2 階建て以上で、階段室や吹抜を通って上下階を行き来できます
(床スラブに開けた穴が、そのまま当たり判定の穴になります)。

| 建物 | 階数 | 寸法 | 内容 |
|---|---|---|---|
| 学校校舎 | 3 階 | 40 × 10.5 m | 普通教室 4 室 + 片廊下 + 両端に階段室 |
| 公民館 | 2 階 | 24 × 16 m | 2 層吹抜のエントランスホール / 事務室 / 和室 / 調理室 / 2F 会議室 |
| 工場 | 1 階 (H=9 m) + 点検通路 | 30 × 20 m | 生産エリア + 配管・タンク・クレーンレール + 高さ 4.5 m のキャットウォーク |
| 事務所ビル | 3 階 | 28 × 14 m | 中廊下 + 執務室 6 室/階 + 西側コア (階段室) |

床・壁・照明は建物ごとに違います。事務所ビルは濃いカーペットなので 4 種のなかで
いちばん暗く、全階が同じ間取り・同じ内装なので「階を取り違えるか」の評価に向きます。
逆に公民館は吹抜から自然光が入って明るめです。

建物モードでは寸法スライダの代わりに「建物」の選択肢が出ます
(寸法は間取りで決まるため)。模様の多さ・家具の量・マーカー・照明・シードは
単室と同じように効きます。

## 建物を作る・再現する

壁・床スラブ・階段・家具・照明・点検対象は、すべて同じ記述
(`src/config/buildings.js`) から**描画と当たり判定の両方**を生成します。
見えている壁には必ずぶつかります。

### 間取りの書き方

平面は X (右) と Z (奥行) の 2 次元、Y が高さ。原点は建物の中心です。
壁は「線分 + 開口」で書きます。

```js
import { wall, door, win, pass, room, roomWalls, target } from './buildings.js';

const H = 3.5;                       // 階高
const floor1 = {
  name: '1F',
  elevation: 0,                      // 床スラブ上面の高さ
  height: H,
  outline: { x0: -20, z0: -5.25, x1: 20, z1: 5.25 },   // 外形

  walls: [
    // 外周 (厚み 0.2 m)
    ...roomWalls(-20, -5.25, 20, 5.25, { t: 0.2 }),
    // 廊下と教室の仕切り。at は壁の始点からの距離 [m]
    wall(-12, -2.75, -4, -2.75, { t: 0.1, o: [door(1.2, 1.6, 2.1), win(4.5, 2.4, 1.0, 1.1)] }),
  ],

  // 家具を置く部屋 (kind で置く家具の種類が決まる)
  rooms: [room('1F 教室1', -11.8, -2.55, -4.2, 5.05, 'classroom')],

  // スラブに開ける穴 = 階段室・吹抜。ここを通って上下階へ移動できる
  voids: [{ x0: -19.7, z0: -4.95, x1: -16.3, z1: 4.95 }],

  // 実際の段板 (見た目と当たり判定)
  stairs: [{ x: -18, z: 0, width: 1.4, dir: 1, rise: H }],
};
```

| 要素 | 意味 |
|---|---|
| `wall(x1,z1,x2,z2,{t,h,base,o})` | 壁。`t`=厚み、`h`=高さ (既定は階高)、`base`=下端、`o`=開口の配列 |
| `roomWalls(x0,z0,x1,z1,opts)` | 矩形を囲む 4 枚の壁をまとめて作る |
| `door(at,w,h)` | 出入口 (床から)。`at` は壁の始点からの距離 |
| `win(at,w,h,sill)` | 窓 (床から `sill` の高さ)。腰壁とまぐさが残ります |
| `pass(at,w,h)` | 開放部 (ホールへの開口など) |
| `room(name,x0,z0,x1,z1,kind,{density})` | 家具を置く範囲。`kind` は `classroom` / `office` / `meeting` / `lobby` / `corridor` / `kitchen` / `storage` / `factory` |
| `target(name,x,y,z,kind,{yaw})` | 点検対象。`kind` は `gauge` / `valve` / `panel` / `joint` |

建物プリセットの直下には次を書きます。

| キー | 意味 |
|---|---|
| `floors[]` | 各階 (上の例の `floor1` の形) |
| `routes` | 自動飛行の経路。`{ patrol: [{x,y,z,yaw}, ...] }` |
| `spawn` | 機体の初期位置 `{x, z}` (省略時はルートの始点) |
| `materials` | `floor` / `corridorFloor` / `wall` / `ceiling` / `exterior` |
| `lighting` | 既定の照明プリセット名 |
| `targets` | 点検対象 (建物全体で 1 つの配列) |

`routes` に通過点を書いておくと、自動飛行の**パターン「建物ルート」**で
そのまま追従できます (壁のある建物では経路計画が要るので、通れる線を
あらかじめ与える方式にしています)。**ルート沿い 0.9 m には家具が置かれない**ので、
経路さえ壁を通っていなければ必ず飛べます。

### 実在の建物を再現する

平面図の寸法をそのまま `wall(...)` の座標に書けば再現できます。手順は:

1. 平面図の基準点を建物中心に置き、m 単位で壁の始点・終点を読み取る
2. ドアと窓を、壁の始点からの距離 `at` として並べる
3. 階段室と吹抜を `voids` に書く (これが無いと上階へ上がれません)。
   天井の穴は自動で真上の階の `voids` に合わせるので、書くのは上階側だけです
4. `routes` に飛ばしたい経路を書く
5. `npm test` で検査できます — 開口が壁からはみ出していないか、
   吹抜が機体の通れる大きさか、**ルートが壁や設備を突き抜けていないか**

5 の検査はかなり効きます。同梱プリセットを作ったときも、
「制御室の壁を突き抜けるルート」「タンクの内側を通るルート」を
このテストで見つけて直しました。新しい建物を足したら必ず走らせてください。

```bash
npm test                                  # 間取りとルートの整合性を検査
node tools/building_check.mjs ./shots     # 実際に描画してスクリーンショットを撮る
```

> **注意** — 同梱の 4 種は日本の公共建築でよくある**標準的な**構成
> (教室 8.0 × 8.0 m、廊下幅 2.5 m、階高 3.5 m など) を組んだもので、
> 実在する特定の建物の図面を写したものではありません。
> 特定の建物を再現する場合は、その建物の平面図から寸法を入力してください。

## カメラを設定する

「搭載カメラ (画像生成)」から解像度・画角・歪み係数・ノイズ量を設定します。
歪みを強くすると、実際に画像の直線が曲がることを確認できます。

プリセット: FPV 広角 / RealSense D435 相当 / VIO 用グローバルシャッタ /
スマホ相当 / 高画質 / 下向きナビカメラ。

実機の画像に近づけるため、次を GPU 上で再現します。

- **レンズ歪み** (Brown-Conrady: k1, k2, p1, p2) — 逆変換を反復で解いて正しく歪ませます
- **周辺減光** (cos⁴ 則)、**倍率色収差**
- **センサノイズ** — ショットノイズ (輝度の平方根に比例) + 読み出しノイズ + 固定パターンノイズ
- **モーションブラー** — 露光時間中の姿勢を補間して積分 (シャッター速度で変わります)
- **ローリングシャッタ**風の行方向スキュー
- 露出・コントラスト・彩度・ホワイトバランス
- **深度マップ**の同時出力

内部パラメータは水平画角と解像度から決まります:

```
fx = (W/2) / tan(hfov/2),   fy = fx × 画素アスペクト比,   cx = W/2,  cy = H/2
```

歪みを含む画像を作るため、**歪みの逆変換を反復で解いて必要な画角を求め、
少し広い画角で描画してから歪ませています**。単純に前方変換を掛ける実装と違い、
出力される歪み係数がそのまま OpenCV / Kalibr の `radtan` モデルとして使えます。

カメラの**取り付け位置と俯角**は「機体 → パーツ → カメラ (機体側)」で変えます
(真下を向けるなら俯角 90°)。カメラと機体の相対姿勢は `metadata.json` に
そのまま入るので、extrinsics として使えます。

## データセットを作る

1. フライトモードを **自動飛行 (auto)** にする
2. 「自動飛行の軌道」でパターンを選ぶ
3. 「データセット記録」で fps と枚数を決めて **記録 開始** (**G** キー)
4. **ZIP で書き出し**

**軌道パターン**

| パターン | 内容 | 向いている用途 |
|---|---|---|
| ホバリング | その場に静止 | ノイズ特性の確認 |
| ウェイポイント | 指定した通過点を平滑に結ぶ | 任意の経路 |
| 往復スキャン | 地面を舐めるように往復 | 地図作成・床面撮影 |
| 螺旋 | 螺旋状に上昇 | 部屋全体を広くカバー |
| 周回 | 注視点まわりを回る | **NeRF / 3DGS 用** |
| 8 の字 | 加減速と旋回が入る | **VIO の評価** |
| 壁沿い一周 | 壁沿いにヨーを振りながら一周 | 壁面の観測 |
| ランダムウォーク | 不規則に移動 | 学習データの多様性 |
| **建物ルート** | 建物に書かれた点検・巡回ルート | **複数階・設備点検** (建物モードのみ) |

**機首の向き**は 固定 / 進行方向 / 注視点を向く / 連続旋回 から選べます。

ZIP の中身:

```
rgb/000000.png ...        画像 (歪み・ノイズ込み)
depth/000000.png          深度 (16bit を R,G チャンネルに分割して格納)
groundtruth.txt           機体の真値軌跡  TUM 形式 (ENU ワールド / FLU 機体)
groundtruth_camera.txt    カメラの真値軌跡
rgb.txt                   タイムスタンプ ↔ 画像の対応 (TUM 形式)
imu.csv                   IMU 観測値 200 Hz (EuRoC 形式, FLU)
camera.yaml / camera.json カメラ内部パラメータ (Kalibr 互換)
transforms.json           NeRF / 3D Gaussian Splatting 用のポーズ
colmap/                   COLMAP 形式のカメラとポーズ (真値なので SfM 不要)
telemetry.csv             機体の全状態量 (速度・姿勢・電圧・回転数…)
metadata.json             生成条件の全設定 (これを読み込めば再現できます)
README.txt
```

IMU は VIO でよく使われるモデル (白色雑音 + バイアスランダムウォーク) で、
ノイズ密度は EuRoC データセット相当の値を既定にしています。

**Python での読み方**は [docs/RESEARCH.md](docs/RESEARCH.md#3-出力の読み方-python) を参照してください
(TUM 軌跡の読み込みと ATE の計算、深度マップの復元、`camera.yaml` の使い方)。

## コマンドラインでの一括生成

条件を変えたデータセットをまとめて作るには、ヘッドレス CLI を使います。
画面表示と同じ描画パイプラインを使うので、目で確認した見た目のまま出力されます。

```bash
npm install playwright && npx playwright install chromium

node tools/render_dataset.mjs \
  --out ./datasets --frames 300 --fps 10 \
  --vehicle research-250 --room lab --pattern lawnmower \
  --speed 0.5 --altitude 1.2 --tilt 90 \
  --width 640 --height 480 --seed 42 --depth
```

刻み幅を固定して 1 ステップ = 1 フレームで進めるため、
**実行環境の速さに関係なく同じデータが得られます** (再現性)。

### オプション一覧

| オプション | 既定値 | 意味 |
|---|---|---|
| `--out <dir>` | `./datasets` | 出力先 |

| `--pattern <key>` | `lawnmower` | 軌道パターン |
| `--yaw-mode <key>` | `along-path` | 機首の向き |
| `--speed <m/s>` | 0.5 | 飛行速度 |
| `--altitude <m>` | 1.2 | 巡航高度 |
| `--radius <m>` | 1.5 | 周回・8 の字などの半径 |

## 物理モデル

6 自由度剛体ダイナミクスを RK4 (既定 500 Hz) で積分します。

**機体構成から自動計算されるもの**

- 質量・重心・慣性テンソル (パーツごとの形状と質量から平行軸の定理で合成)
- ロータ配置 (位置・回転方向・推力軸)
- 制御配分行列とその疑似逆行列
- 制御ゲイン

**モデル化されている現象**

| 分類 | 内容 |
|---|---|
| ロータ | 推力 `T = Ct ρ n² D⁴`、反トルク `Q = Cq ρ n² D⁵` |
| モータ | 一次遅れ (加速・減速で別時定数)、個体差、故障注入 |
| バッテリー | SOC 曲線、内部抵抗による電圧降下、消費電力積算 |
| 地面効果 | 床に近いと推力増加 (最大 1.35 倍) |
| 天井効果 | 天井に吸い寄せられる (最大 1.5 倍) |
| 壁効果 | 壁際で横方向に引き込まれる |
| 並進揚力 | 水平移動で誘導速度が下がり推力増加 |
| VRS | 急降下時の推力損失 (近似) |
| ロータ抗力 | ロータ位置での局所対気速度による H-force。**角速度の減衰もここから自然に生じます** |
| ジャイロ | 回転するロータの角運動量によるモーメント |
| 室内気流 | 定常流 + Ornstein-Uhlenbeck 過程の乱流 + 空調吹き出し口 + 床付近の境界層 |
| 接触 | バネ・ダンパ + クーロン摩擦。機体各所に配置した球で判定 |

**センサ**: IMU (200 Hz, ノイズ密度・バイアスランダムウォーク・スケール誤差・
飽和)、気圧計、下向き ToF、オプティカルフロー (高さとテクスチャ量に依存)、
磁気センサ (屋内の磁気外乱付き)。

**制御配分**は「再配分疑似逆行列法」です。上下限を超えたロータを順に固定して
解き直すので、飽和時も姿勢トルクを可能な限り実現します。
自由なロータが足りなくなるとヨー要求を段階的に (100% → 50% → 20% → 0%)
諦めます。屋内では機首方位より姿勢と高度の維持が重要なためです。

物理コア (`src/core/`) は three.js に依存しないので、Node.js から直接呼んで
バッチ実験もできます ([例](docs/RESEARCH.md#7-物理側の実験にも使えます))。

## 座標系

内部座標系は three.js と同じ右手 Y-up です。

```
ワールド W : X = 右(東), Y = 上, Z = 手前(南)
機体     B : x = 右,    y = 上, z = 後方   (前方 = -z, 推力 = +y)

ロール φ : 前方軸まわり、右下げが正
ピッチ θ : 右軸まわり、機首上げが正
ヨー   ψ : 上軸まわり、上から見て反時計回りが正
オイラー角の合成順序: intrinsic Y-X-Z (ヨー → ピッチ → ロール)
```

データセット出力時には `src/core/frames.js` で標準的な規約へ変換します。

| 出力 | 規約 |
|---|---|
| `groundtruth.txt` | ENU ワールド / FLU 機体 (ROS REP-103) |
| `imu.csv` | FLU 機体 |
| `transforms.json` | OpenGL カメラ (x=右, y=上, z=後) の camera-to-world |
| `colmap/` | OpenCV カメラ (x=右, y=下, z=前) の world-to-camera |

変換は単体テストで検証しています (`tests/math.test.js`)。

## 開発と検証

```bash
npm start                              # 開発サーバ (http://127.0.0.1:8080/)
npm test                               # 単体テスト 75 件 (Node.js のみ、数秒)
npm run smoke                          # ブラウザでの動作確認 (要 playwright)
node tools/building_check.mjs ./shots  # 建物のスクリーンショットを撮る
```

**`npm test`** — three.js に依存しない部分をすべて検査します。

| 対象 | 内容 |
|---|---|
| 数学 | 座標変換 (ENU/FLU・OpenCV/OpenGL)・疑似逆行列・クォータニオン |
| 機体 | 質量・慣性テンソル・ミキサ・StampFly の実測値との一致・機体の差し替え |
| 衝突判定 | 描画 (three.js) と当たり判定の向きが一致するか |
| 間取り | 開口・吹抜の寸法・**ルートが壁や設備を突き抜けないか** |

**`npm run smoke`** — 実際に Chromium で読み込み、全機体プリセット・全パーツ形状・
全ロータ配置・全部屋・全建物を一巡させて、例外が出ないこと・メッシュと当たり判定が
生成されること・**画像の露出が妥当な範囲にあること**を確認します。
playwright が要ります (`npm install playwright && npx playwright install chromium`)。

## 困ったときは

| 症状 | 原因と対処 |
|---|---|
| 画面が真っ黒 / 何も出ない | `file://` で開いていませんか。ES モジュールを使うので HTTP サーバが要ります (`npm start`、または `python3 -m http.server`) |
| 「初期化に失敗しました」 | WebGL2 が使えない環境です。ブラウザを更新するか、ハードウェアアクセラレーションを有効にしてください |
| 動きが重い | [描画が重いとき](#描画が重いとき) を参照 |
| 機体がすぐ落ちる / 暴れる | 計器表示の**推力重量比**を確認してください。1.5 未満は赤字で警告が出ます。パーツを重くしすぎたか、プロペラが小さすぎます |
| 機体が壁を突き抜ける | 「表示 → 当たり判定を表示」で当たり判定を見られます。極端に速い場合は「シミュレーション → 物理レート [Hz]」を上げてください |
| 建物モードで壁にぶつかる | 「建物ルート」以外のパターンは壁を考慮しません。建物では `route` を使ってください |
| 建物の中が暗い | 事務所ビルは意図的に暗い設定です。「環境 → 照明 → 明るさ倍率」で実際の明るさを、「環境 → 照明 → 露出 (表示)」で見た目だけを変えられます |
| 記録した画像に軌道の線が写る | 写りません (補助表示は機体カメラから除外しています)。写るなら不具合です |
| `render_dataset.mjs` が動かない | `npm install playwright && npx playwright install chromium` が必要です |
| CLI が別の環境と違う結果になる | `--seed` を揃えてください。シードが同じなら配置・ノイズ・乱流まで一致します |

## 描画が重いとき

描画コストの大半は「シーン全体を何回描き直すか」で決まります。1 フレームあたり:

```
主描画 1 回
  + 影 (影を落とす光源の数 × 影の更新レート / 表示 fps)
  + 機体カメラ (モーションブラーの枚数 × カメラ更新レート / 表示 fps)
```

影は光源ごとにシーンをもう一度描くので、光源 4 つなら影だけで 4 回ぶんになります。
モーションブラーも露光中の姿勢を積分するため、6 枚設定なら 6 回ぶんです。

さらに、1 回の描画そのもののコストは**画素数 × 光源の数**でほぼ決まります。
three.js の前方レンダリングでは、光源は 1 つ残らずすべての画素で評価されるからです。
建物は室ごとに灯具を置くので光源が 30 灯を超えます。単室 (10 灯前後) より
建物のほうが重いのは、主にこれが理由です。三角形数は建物でも 1 万程度しかなく、
最近の GPU では効きません。

効く順に、「表示」から調整できます。

| つまみ | 既定 | 効果 |
|---|---|---|
| **描画解像度** | 1.5 | **最も効きます。**画素数はこの 2 乗で効くので、1.5 → 0.75 で描画コストは約 1/4 になります。高 DPI の画面ではまずここを下げてください |
| 影の更新レート [Hz] | 15 | 下げるほど軽い。部屋は静止しているので、下げても変わるのは自機の影の追従だけ |
| カメラ更新レート [Hz] | 30 | 機体カメラ (PiP) の更新頻度。記録する fps より下げなければ問題ありません |
| カメラ映像を重ねる | on | 切ると機体カメラのパスが丸ごと無くなります (一人称視点でも記録中でもないとき) |
| 搭載カメラ → モーションブラー → サンプル数 | 6 | 露光中の描画枚数。1 にすればブラー無しで最も軽くなります |
| 環境 → 照明 → 影の解像度 | 低 (1024) | 影 1 枚あたりのコスト。4 灯ぶん焼くので 2048 にすると深度の描画量は 4 倍 |
| 環境 → 照明 → 影を落とす | on | 切れば影のパスが丸ごと無くなります |
| 環境 → 家具の量 | 1.0 | 頂点数が減ります (統合済みなのでドローコールは増えません) |

### 建物で見えていないところを描かないしくみ

建物は複数階あるので、そのままでは**スラブの向こう側の階まで毎フレーム描かれます**。
視錐台カリングは視界の外しか落とせず、遮蔽 (壁やスラブの裏) は判定しないためです。
2 段構えで削っています。

- **静的メッシュの統合を 8 m 四方のセル単位で行う** — マテリアルごとに 1 つへ
  まとめるとドローコールは減りますが、境界球が建物全体に広がって視錐台カリングが
  効かなくなります。セルに分けることで、両方を成立させています。
- **離れた階を描かない** — 視点のいる階の ±1 階だけを表示します。外部視点と
  機体カメラでは高さが違うので、それぞれ描く直前に切り替えています。
  俯瞰視点では全階を出します。

影は隠している階からも落ちてほしいので (階段の吹抜など)、焼くときだけ全階を
出しています。学校で描画される三角形は 8076 → 5362、事務所ビルは 15234 → 10032 に
減りました (廊下を見通す視点での実測)。

**ホバリング中はモーションブラーを自動で省きます。** 露光中のブレが 1 画素に
満たないときは積分しても同じ絵になるので、1 枚で済ませています。
そのため、止まっているときと飛んでいるときで負荷が変わります。

### 手元の環境で内訳を測る

どの段が重いかは GPU・解像度・環境で変わります。ブラウザの開発者コンソールで:

```js
await app.profile()
```

主描画 / 影の焼き直し / 機体カメラ (ブラーあり・なし) をそれぞれ計測し、
mesh 数・三角形数・光源数と合わせて表で出します。
最後に「60fps 時の 1 フレーム見込み」も出るので、どこを削れば効くか判断できます。

開発用のツールも入っています (要 playwright)。

```bash
node tools/perf.mjs          # 環境ごとの mesh 数・シーン走査回数・所要時間
node tools/perf_lights.mjs   # 光源の数が描画コストに与える影響
node tools/merge_check.mjs   # ジオメトリ統合の前後で描画が変わらないかの回帰確認
```

## 既知の挙動と制限

**これは「仕様どおり」の挙動です**

- **ヘキサコプターのロータを 1 基止めるとヨーが回り続けます。**
  標準的なヘキサは 1 基を失うと 4 自由度すべてを制御できません。
  本シミュレータはヨーを諦めて高度と姿勢を維持する挙動を再現します
  (実機の motor-out と同じ)。数秒後には回転が速くなり姿勢も崩れます。
- **トライコプターはホバリング時にわずかに傾きます。**
  テールロータを傾けてヨートルクを作るため、その水平成分で機体が傾きます。
  実機のトライコプターと同じ現象です。
- **StampFly は推力重量比 1.49 と低い**ので、急上昇と大きな姿勢変化を同時に
  要求すると出力が飽和します。実機と同じです。
- 機体カメラには既定で自機が写りません (カメラが筐体内部にあると
  内側が見えてしまうため)。「表示 → 自機を映す」で変更できます。

**制限**

- 建物プリセットは日本の公共建築の**典型的な**構成で、実在する特定の建物ではありません。
  実在の建物を再現する場合は、その平面図から寸法を入力してください
  ([建物を作る・再現する](#建物を作る再現する))。
- 建物モードには経路計画がありません。自動飛行では `routes` に書いた
  通れる経路を追従します (壁を避けて自動で回り道はしません)。
  「建物ルート」以外のパターン (往復スキャン等) を建物モードで使うと壁にぶつかります。
- 建物の照明は室ごとに 1〜4 灯で、合計 28 灯を上限にしています。
  実際の建物より灯数は少ないので、細長い部屋の端はやや暗くなります
  (足りない分は相互反射の近似として半球光で底上げしています)。
- 壁・階段・家具などの動かないメッシュは、マテリアルごとに 1 つへ統合しています
  (`src/render/geometryMerge.js`)。ドローコールが 4〜6 分の 1 になる代わりに、
  統合後は個々の家具を動かせません。視錐台カリングの単位も階ごとになります。
- 家具の色は 8 段階に離散化しています。マテリアルを使い回して統合できるように
  するためで、実物の家具が数種類の色しかないのと同じ考え方です。
- 大域照明 (GI) は環境マップによる近似です。壁からの照り返しは簡略化されています。
- 空力は準定常モデルです。ロータ間の干渉や渦の詳細は扱いません。
- 一人称視点を全画面表示しているときだけ、自機の影が機体カメラの画像に写りません。
- ローリングシャッタは行方向のスキューによる近似で、走査中の再投影はしていません。
